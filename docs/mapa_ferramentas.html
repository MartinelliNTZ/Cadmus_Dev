Uma ferramenta, uma entrada rastreável

O Cadmus tem duas portas oficiais: o ToolRegistry para ferramentas de menu/toolbar e o MTLProvider para algoritmos do Processing. As duas usam ToolKey como identidade.

Descoberta

  • ToolKey identifica a ferramenta.
  • ToolRegistry registra nome, categoria, tipo e executor.
  • MTLProvider registra algoritmos no Processing.
  • Preferências e logs usam a mesma identidade.

Execução

  • Dialogs herdam de BasePluginMTL/BaseDialog.
  • A UI usa widgets de resources/widgets.
  • Map tools recebem eventos do canvas.
  • Processing usa BaseProcessingAlgorithm.

Resultado

  • Camadas, arquivos, relatórios ou alterações no projeto.
  • Mensagens pelo sistema de comunicação do Cadmus.
  • Preferências persistidas quando aplicável.
  • Logs rastreáveis pelo tool_key.

Como manter este mapa vivo

Este HTML é documentação técnica para a equipe. Ele deve acompanhar o sistema, não uma entrega isolada.

Quando atualizar uma ferramenta

  • Altere a ficha correspondente quando houver mudança funcional relevante.
  • Revise finalidade, fluxo, entradas, saídas, widgets e dependências afetados.
  • Se a família ou a forma de entrada mudar, revise também a arquitetura e os contadores.

Quando criar uma ferramenta ou widget

  • Inclua toda ferramenta nova no array TOOLS, com número visual gerado pela ordem da lista.
  • Inclua todo widget novo no array WIDGETS, com camada, arquivo, responsabilidade e exemplo.
  • Preserve a separação: a ferramenta documenta seu uso; o widget documenta seus controles internos.

Mapa técnico ≠ tooltip de usuário

  • Este documento explica arquitetura e funcionamento para desenvolvedores.
  • A ferramenta é dona da descrição contextual dos itens que declara, como cada checkbox de um GridCheckbox.
  • O widget é dono da descrição dos controles internos que ele próprio cria, como botões internos de um ComplexSelector.
  • Tooltips reais continuam tokenizadas e em Strings_pt_BR; não copie o texto deste mapa diretamente para a interface.

Padrões que atravessam o catálogo

Abaixo estão os componentes compartilhados que aparecem em várias ferramentas. Eles são os pontos certos para entender uma mudança transversal.

Widgets de entrada

  • GridComplexSelector: arquivo, pasta, camada, origem e saída.
  • GridInputFields: campos textuais em dicionário.
  • GridComboBox/GridRadioButton: escolhas declarativas.
  • GridDoubleSpin/GridSlider/GridDateSelector: valores especializados.
  • GridBBoxSelector: extensão por camada, tela ou desenho.

Widgets de ação

  • GridExecutionButtons: execução, fechar, info e config.
  • GridModernButtons/GridIconButton: ações auxiliares.
  • GridCheckbox: opções e seleção em lote.
  • GridAttributeSelector: campos vetoriais com controles próprios.
  • ListSelectionDialog/SceneSelectionListWidget: seleção de itens complexos.

Persistência e contexto

  • Plugins carregam e salvam preferências com Preferences.
  • Widgets com estado próprio expõem get_preferences()/set_preferences().
  • Processing usa BaseProcessingAlgorithm para preferências e ajuda.
  • O tool_key acompanha logs, tarefas e diálogos.

Camadas de suporte

  • BaseDialog fornece MainLayout.
  • AppStyles/ThemeManager fornecem estilo.
  • InstructionsManager resolve ajuda de plugins.
  • HtmlInstructionsProvider resolve ajuda de Processing.
